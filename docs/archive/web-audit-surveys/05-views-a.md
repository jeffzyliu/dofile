## 2. Shape
One Preact tree for every width (App.tsx); phone pieces are conditionals inside it, and components read `isPhone`. Editor.tsx mounts one CodeMirror view and keeps one `EditorState` per open text tab; the file list calls it through the mutable `editorCommands` object (commands.ts). The log is a pure render of the `log` signal; streaming works by replacing the run's text item in the signal (run.ts:158), not by DOM appends. Pure helpers (classify, align, paste, ranover, errormark, words, keys) are tidy and unit-tested. **The risk is in Editor.tsx** (per-path bookkeeping, ordering with the file controller, focus) **and LogView.tsx** (scroll-follow, Find, a 125-line render function).

## 5. Redesign question
Yes, one, and it is W1: pull the per-file editor bookkeeping out of Editor.tsx into one record per path and a DOM-free controller. Evidence so far: `open`, `reload`, `ranOver`, `renamed`, `closed` and `save` touch the view only through `current()`, `update()` and `show()`, and `@codemirror/state` has no DOM, so this looks possible. It would remove F1/F2 (one record to rename or close, ordering stated in one function) and bring the logic that has caused the most special cases (rename vs save vs delete, run vs unsaved edits) under unit tests instead of e2e only. Cost: M, medium risk, and it must keep the `editorCommands` contract. It would not touch focus. I would do it, after W2, because every later change to saving or tabs otherwise means editing 10 sites in one 500-line file. Unchecked: whether `cm.ts` loads under Node (`@codemirror/view` import); the controller can avoid it by taking `stateFor` as a parameter.
