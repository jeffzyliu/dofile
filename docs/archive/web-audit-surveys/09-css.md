## 4. The ui.css / app.css division
Stated intent (ui.css:1, app.css:1-3): ui.css = "components, on the tokens, used by the page and the design pages"; app.css = "the editor page's layout". docs/design/README.md says ui.css began as the design mockups' CSS and moved to `web/src/styles/` on 2026-11-10, i.e. the rule is "mockup CSS (kept shared so docs/design/ still renders) vs what the app added". It is only partly a real rule: app.css opens with layout, but 70% of it (lines 283-1275) is component styling for the app's own features (CodeMirror, log buttons, find bar, command line, phone strip, viewer, files rename, dta view), added "as drawn" on top of ui.css. Rules for one component in both files (5 of 17 same-selector pairs):
1. `.cmdline .field`: ui.css:845-853 (muted mockup) and app.css:977-1003 (ink; disabled; focus).
2. `.files li`: ui.css:500-508, 518, 593; app.css:572-590 (cursor, name/size/rename).
3. `.rs .copy`/`.rs .row td`/`.rs .fold`: ui.css:1190-1233 vs app.css:525-540, 554-560.
4. `.thumb`, `.thumb.on`, `.graph-foot`: ui.css:886-896, 879-885 vs app.css:380-396, 548-550.
5. Editor line marks: ui.css:682-700 (`.code .ln.run/err`) vs app.css:823-839 (`.cm-run-line/.cm-err-n`): same design, two implementations.
Also `.toolbar` (ui.css:151, app.css:63), `.pane`, `.pane-body`, `.log .head .art`, `.t .var`, `html`, `body`.
Overrides that exist only to undo ui.css: `.cmdline .field` colour (app.css:978, comment says so), `.statusbar`-less, `.app[data-layout=phone] .pane { border:0; border-radius:0 }` (app.css:234, undoing `.pane`), `.app[data-layout=phone] .key {display:none}` (hides ui.css `.key`), `:root[data-keyboard] .app .views {display:none}`, `.log.wrap .head ... white-space` resets (1191-1197), toast `bottom:auto; transform` resets (C8), `.pane-head` hidden on phone (239-243). Those are intentional per-layout overrides, not specificity fights.

## 6. Phone vs desktop, state, tokens
- Mechanisms (three): (1) attribute `data-layout="phone"` on `.app` (24 selectors, all in app.css), driven by a JS signal; (2) `@media (max-width: 699.98px)` x4 (app 45, 461, 1229; ui 1362) and site.css `max-width: 700px`; (3) `isPhone` in 13 TSX places choosing markup. Plus `(pointer: coarse)` x4 for 44 px targets and `(hover: hover|none)` x15, `container` queries x3 (424px, 290px, 340px, magic numbers beside the content they clip). Media-query census: 39 `@media`/`@container` blocks; distinct width breakpoints: 699.98px, 700px, 55.99em, 1199.98px, 359px, container 424/290/340 = 8. The phone breakpoint is not stated once: it is in main.tsx:42 plus 5 CSS spellings.
- State via attributes: `<html data-engine>` is used by one CSS rule (C7). Other attributes set from JS: `data-keyboard` (viewport.ts), `data-theme`, `data-layout`, `data-split` (app.css:98), `data-files` (203-207), `data-drop` (FilesPane.tsx:574 via `dataset`, so a plain grep for `data-drop` in TSX misses it), `aria-*` (expanded, disabled, invalid, selected, checked) as styling hooks. These are a reasonable pattern; the one unsafe use is prefix-matching an engine state name.
- Tokens: raw hex outside tokens.css: 0 (all three files). Raw z-index outside tokens: site.css 10 and 5; app.css 1 x2 (justified by a comment about `.cm-scroller`). `--z-menu` is also used for `.viewer` (app.css:408), though the comment calls it "under the toast". 44px x20, 61px x2, `border-radius: Npx` x7 raw (`14px` sheet radius x2, `4px`, `9px`, `999px`), `animation: spin 1s` raw duration (tokens has `--dur`). Tokens exist for control height, strip, pane head, bar, shadows; none for the "finger target" (44) or the tab bar height.
- Clone in tokens.css 152-174 vs 176-198: it is the dark palette in the media query and again under `[data-theme="dark"]`. Could it be stated once? Yes, but only by changing mechanism: (a) a `light-dark()` per token (`--bg: light-dark(#f7f7f5, #14161b)`) with `color-scheme` set by `:root[data-theme]` (app.css:5-13 already sets `color-scheme: light dark` / light / dark), which makes the two copies disappear and halves the file (needs baseline browser support for `light-dark()`: 2024+, so Safari 17.5+; unknown whether the project's browser floor allows it); (b) a PostCSS/Vite step to emit the second copy; (c) keep as is, tested. Option (a) changes how the engine resolves colours, not the values, so `contrast.mjs` (which resolves tokens in four modes) would verify it.

## 9. Redesign question
Not a redesign: the structure is workable. The one structural change I would consider is making `data-layout` (or a class) on `<html>` the single phone switch and deleting the JS `matchMedia` duplication of CSS width numbers (or the reverse: generate the CSS number from one constant), because that removes C1's silent drift and lets `<dialog>` use the same selector. Cost: M, touches app.css (24 selectors), ui.css 1 block, main.tsx:42; breaks nothing if done with W1's baseline. I would do it as W3 after W1, not now. A split of app.css into per-component files (editor.css, log.css, files.css, output.css) is the second candidate; it needs no design change and is worth doing only alongside W5, since Vite handles many imports fine.

## 10. What is good
Colour tokens are fully respected (0 raw hex outside tokens.css, 0 unused custom properties); `:where()` keeps specificity flat; `!important` is 3 uses; all hover is guarded and tested (`imports.test.ts`); `contrast.mjs` resolves every theme mode; forced-colors and reduced-motion are handled in-place next to each component. The tokens-as-source with design checks is worth keeping.
