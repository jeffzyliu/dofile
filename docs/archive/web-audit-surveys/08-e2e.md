# 08 - End-to-end suite (web/e2e/)

## 1. Covered
Read fully: fixtures.ts, global-setup.ts, playwright.config.ts, poc.spec.ts, main.tsx. Read in part: editor.spec.ts lines 1-58, files.spec.ts 20-70, step2.spec.ts 1-60, workflow web.yml 100-140, docs/test-map.md excerpts. For the other specs I read only the test names (grep) and counting greps. NOT read: the bodies of almost every test (about 95% of 8.6k lines), graphics, keyboard, landing, output, states and shell bodies, commands.spec, fixtures.spec. Commands: grep, sed, cat only. No test run.

## 2. Shape
About 230 tests in 14 spec files. Each runs in four Playwright projects (chromium, firefox, webkit, iphone), one CI job per project. Almost every test boots the page with `?test` or `?test=manual`, seeds files through `window.__dofile.store.write`, then drives the UI with real clicks and keys and asserts through roles, a few CSS classes, and the hook's signals. Only fixtures.ts is shared (persisted-storage stub, `retryFirstGoto`, `startEngine`). Risk files: editor.spec.ts (2489 lines, 45 tests, huge titles) and files.spec.ts (1595, 68 tests). Both carry their own setup helpers and a hand-typed `Hook` type.

## The hook `window.__dofile` (main.tsx, only with `?test`)
Keys: `engine` (EngineClient), `store`, `start`, `persisted`, `engineBytes`, `state` (the whole state.ts namespace), `run`, `breakRun`, `reset`, `selection`, `drops`, `focusWanted` (from FilesPane.tsx).
Usage by spec (`__dofile` mentions): editor 139, states 58, step2 38, shell 25, output 24, files 20, engine 15, sample 10, keyboard 7, graphics 5, landing 2.
Key use counts: `state` 183, `store` 65 (`write` 20, `blocked` 12, `list` 9, `read` 6, `zip` 3, `remove` 2), `run` 21, `engine` 12 (`worker` 6), `start` 8 (plus fixtures.ts), `drops` 6, `breakRun` 4, `selection` 3, `reset` 2, `persisted`/`engineBytes`/`focusWanted` 1 each.
Mostly OBSERVE (tabs, lastRun, history, log, files, banners) or SEED (`store.write`, `runWriter`, `addBanner`). Where it DRIVES where a user could not: `state.engine.value = ...` (see E2), `state.dialog.value = {d:"close-tab"...}` (editor:180,1485; files:1192,1380: the dialog is opened without the user action that opens it, so the test does not prove that the app opens it), `phoneTab`/`split`/`outputTab`/`theme`/`graphFull` writes, `__dofile.run(code)` (runs as `test.do`, bypassing the command line, run-head and editor; used by graphics, output, step2). Most tests that claim to test a flow do click it. Risk: seeded states stay reachable only if the real transitions are tested elsewhere (engine.spec, states.spec do cover several).

## Per-browser cost
Four projects: chromium, firefox, webkit (Desktop Safari, navigationTimeout 60 s), iphone (iPhone 15, a WebKit emulation). CI runs one job per project (web.yml:115-120, 30 min limit, "under 10 minutes" each). Every spec runs in all four except by test-level skips. Proportionality: the engine-boot tests (engine, graphics, sample, step2, editor with `?test`) are the expensive ones, and they run 4x although the engine is the same Python in the same Pyodide; the three desktop projects differ only by browser quirks (WebKit focus, Firefox scroll). The pure layout and phone tests run correctly on iphone/chromium. Candidate: run the engine and graphics specs on chromium and one WebKit only (about 40 tests), and keep the DOM specs on all four, since focus and key handling differ by browser and the refactor touches exactly that. Landing/commands specs (about 24 tests, static pages, axe) need only chromium + iphone. I could not measure time, so this is a guess.

## 5. Redesign question
No structural redesign of the suite. Do ONE thing: put the hook's contract in one typed file (item 2) and make the e2e hook a deliberately small, named surface (seed files, read store, read engine state, `run`) instead of the whole `state` namespace. Then the tests keep working when state.ts is restructured, and drive-through-signal use (E2) is limited to a few named helpers (`showEngineState(...)`, `openDialog(...)`) that state in one place what is faked. Cost: about 1 day, because ~180 `state.*` uses need a helper each, many mechanical. It breaks nothing in the app (the hook only exists under `?test`). I would do it, but before the view refactor only the typing (item 2) and the helper wrappers for the 25 signal writes; the observation uses can stay.

## 6. What is good
Role-and-name selectors dominate (557 `getByRole`), so most tests survive a component split. Failure-mode coverage is specific (CRLF bytes, rename races, focus handoff, held key repeats). `fixtures.ts` is small and documented. `global-setup.ts` refuses a stale or wrong-address build. docs/test-map.md maps the suite. No `retries`, no `toPass`, no `test.only`, and skips each state a reason.
